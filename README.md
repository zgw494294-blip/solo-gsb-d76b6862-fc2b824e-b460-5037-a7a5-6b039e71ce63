# LED 混光配方台（本地）

以 **OR-Tools CP-SAT** 精确求解多通道 LED 混光的**最小总功率**配方，并可
联合规划从起始驱动级到目标色的**最小总功率调光路径**；
**Python / FastAPI** 提供接口，页面为**原生 HTML / CSS / JavaScript**（无前端框架、无构建步骤）。

## 一条命令启动

```bash
docker compose up --build
```

启动后浏览器访问：

- 配方台页面：<http://localhost:8000/>
- 接口文档（Swagger UI）：<http://localhost:8000/docs>
- 健康检查：<http://localhost:8000/api/health>

停止：`Ctrl+C`（后台运行则用 `docker compose down`）。端口在
`docker-compose.yml` 中映射为宿主机 `8000`，如被占用可改成 `"8080:8000"`。

不使用 Docker 时也可本地运行（Python 3.11）：

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## 使用说明

1. **通道录入**：3～6 路 LED，ID 唯一。
   - 满档线性 RGB：`0～1000` 整数，三色**不全为零**；
   - 满档功率：`1～10000 mW` 整数；
   - 可随时增删通道（3 路时禁止再删、6 路时禁止再加），“载入示例”恢复内置样例。
2. **目标与容差**：目标线性 RGB 各为 `0～1000` 整数，共用整数容差 `0～20`。
3. 点击 **“求解最省功率配方”**：
   - 有解时显示目标/实际色块（标准 sRGB 传递函数）、各路驱动级、
     分量误差、逐路功率贡献与总功率；
   - 驱动级可直接手动修改，页面会按精确公式实时预览色块/误差/功率，
     “恢复最优驱动级”一键回到最优配方；
   - **无可行解时给出明确提示，不返回任何近似配方。**
4. **单路熄灭容错配方（③）**：沿用当前 3～6 路通道、② 的目标线性 RGB
   与共用容差，再输入**故障后每路允许调整的最大驱动级差**（`1～255`），
   点击 **“规划容错配方”**：
   - 同时求出**正常驱动级**与**每一路**单独熄灭后的**备用驱动级**：故障路
     强制为 0，其余各路与正常值之差不超过上限；正常与全部备用配方都按
     现有未裁剪公式落在目标 ± 容差且 `0～1000` 内；
   - 目标是在**具备全部备用配方**的正常方案中最小化**正常总功率**，
     同功率时正常驱动序列按 ID 升序取字典序最小（备用方案只需可行）；
   - 页面展示正常配方（色块/驱动/分量误差/功率）与逐路熄灭卡片
     （故障路标红、正常→备用驱动及 Δ、备用实际色与误差、备用功率）；
   - **无完整方案时不返回正常配方，也不返回任何部分备用**（会明确说明
     是哪一路熄灭后无法配色、还是调整上限下的联合约束不可行）；
     **搜索未证明最优时报告“搜索未完成”**，同样不返回任何驱动级；
   - 通道、目标、容差或调整上限任一项改变后，旧容错结果自动清除。
5. **满档读数标定（④）**：不知道各路满档线性 RGB 时，在 3～6 路通道下
   录入 3～12 组实测样本——每组给出各路 `0～255` 整数驱动级与实测
   `0～6000` 整数线性 RGB，点击 **“反求满档读数”**：
   - 实测值按 `实际值 = Σ(满档读数 × 驱动级) / 255` 后**四舍五入到整数**解释，
     后端用 CP-SAT 整数约束反求每路 `0～1000` 满档 RGB（各路三色不全为零）；
   - **样本矛盾**、**标定不唯一**（存在多组合法参数）、**搜索未完成**
     三种情况都会明确报告，且不显示任何参数；**只有证明唯一时**才列出
     反求结果、逐样本实测残差，并开放 **“一键写回当前通道表”**
     （只覆盖满档 RGB，**保留各路原功率**），写回后即可正常求解配方；
   - “按当前通道生成示例样本”可依据当前通道表的满档值合成每路单独
     满档点亮的示例；非法样本（越界、数量不符、ID 问题等）前端与
     接口都会明确拒绝（HTTP 422）。
6. **调光路径规划（⑥）**：以当前通道表为准，按 ID 录入各路 `0～255`
   **起始驱动级**，再录入终点线性 RGB（`0～1000`）、等时步骤数（`2～5`）
   与每步每路驱动变化上限（`1～255`），容差沿用 ② 的共用容差，点击
   **“规划最小功率调光路径”**：
   - 起点实际色按未裁剪公式计算；第 k 步参考色为起点实际色到终点按
     `k/步骤数` 的线性插值（**不先取整**）；每步实际 RGB 须落在参考色
     ± 容差且 `0～1000` 内，相邻两步（首步与起点）每路驱动变化不超过上限；
   - 后端**联合**求解各步功率之和最小的**完整路径**，按时间轴展示起点与
     各步的实际/参考色块、驱动级（含逐步 Δ）、分量误差与逐步功率；
   - **无完整路径时不返回任何局部步骤；搜索未证明最优时报告“搜索未完成”**；
   - 通道或任一路径参数（含 ② 的容差）变更后，旧路径结果自动清除。

## 数学模型

每路通道 i 的驱动级为整数决策变量 `d_i ∈ [0, 255]`。

- 各色实际线性分量（**不裁剪、不做四舍五入**）：

  ```text
  actual_c = (Σ_i reading[i][c] · d_i) / 255
  ```

  约束（两边同乘 255，全部写成整数线性式，令 `s_c = Σ_i reading[i][c] · d_i`）：

  ```text
  255·(target_c − tolerance) ≤ s_c ≤ 255·(target_c + tolerance)
  0 ≤ s_c ≤ 255·1000
  ```

- 总功率（mW）：

  ```text
  P = (Σ_i power_i · d_i) / 255
  ```

CP-SAT 分两阶段精确求解（见 `app/solver.py`）：

1. **最小化** `Σ_i power_i · d_i`（分母 255 为正的常数，不影响最优性）；
2. 在总功率等于最优值的解中，最小化按 **ID 字符串升序**排列的驱动级序列的
   **字典序**。实现上以 256 为基把序列编码为单个整数目标
   （每位数字 0～255 严格小于基数，编码与字典序一一对应；6 路时最大值
   `256⁶ − 1 ≈ 2.8×10¹⁴`，int64 安全）。

模型判定为不可行时，接口返回 `feasible: false` 且不带任何配方；
仅当 CP-SAT 确认最优（OPTIMAL）时才返回方案。

### 单路熄灭容错配方的整数模型

沿用通道 `i`（`n = 3～6`）的满档读数 `reading[i][c]` 与功率 `power_i`，
给定目标色 `target`、共用容差 `tol` 与故障后每路最大调整级差
`Δ_adj ∈ [1, 255]`。决策变量为 `n+1` 个场景的驱动级：

- 场景 0（正常）：`d[0][i] ∈ [0, 255]`；
- 场景 `f`（`f = 1..n`，第 `f` 路熄灭）：`d[f][f-1] = 0`，
  其余 `d[f][i] ∈ [0, 255]`。

每个场景都须满足与普通配方完全相同的颜色窗口（未裁剪公式，令
`s_q_c = Σ_i reading[i][c]·d[q][i]`）：

```text
255·(target_c − tol) ≤ s_q_c ≤ 255·(target_c + tol)
0 ≤ s_q_c ≤ 255·1000
```

备用场景相对正常方案的调整幅度（故障路恒为 0，天然满足）：

```text
|d[f][i] − d[0][i]| ≤ Δ_adj
```

目标：在全部 `n+1` 个场景均可行的正常方案中最小化正常功率分子
`Σ_i power_i · d[0][i]`，再以与普通配方相同的 256 基数编码对
**正常**驱动序列（ID 字符串升序）做第二阶段字典序最小化；备用配方
不参与目标，只需可行。

正式求解前做 `n+1` 次**单场景预求解**（见 `app/robust_solver.py`）：
正常场景的最小功率作为主模型的合法下界以加速最优性证明；某个熄灭
场景在“仅固定该路为 0、不限制调整幅度”下就不可行时，直接判定整体
不可行并报告具体通道。结论三态：`optimal` 返回正常方案与**全部**
`n` 个备用配方；`infeasible`（含单场景不可行或调整上限耦合不可行）
与 `incomplete`（搜索未证明最优）都**不返回正常方案，也不返回任何
部分备用配方**。

### 满档读数标定的整数模型

设通道 i 的满档读数为待求整数 `x[i][c] ∈ [0, 1000]`（每路三色不全为零）。
样本 s 在颜色 c 上的精确线性值与实测解释为：

```text
y[s][c] = (Σ_i x[i][c] · d[s][i]) / 255
实测 m[s][c] = round_half_up(y[s][c])      ⇔   m − 1/2 ≤ y < m + 1/2
```

两边同乘 `2·255 = 510`，全部写成整数线性约束（令
`S[s][c] = Σ_i x[i][c] · d[s][i]`，无浮点变量）：

```text
255·(2m − 1) ≤ 2·S ≤ 255·(2m + 1) − 1
```

`m = 0` 时该式自动等价于 `S ≤ 127`（即 `y < 0.5`），无需特判。
CP-SAT 两次求解给出**可证明**的三态结论（见 `app/calibration.py`）：

1. 先求任一组合法参数：判定不可行 → **样本矛盾**；超时未找到也未证伪
   → **搜索未完成**（`unknown`，不得报告矛盾或唯一）；
2. 在原约束上追加“至少一个格子与候选解不同”的析取约束：判定不可行
   → 候选解是**唯一**合法参数；找到第二个解 → **标定不唯一**；
   超时 → **搜索未完成**。

只有 `unique` 时页面才展示反求参数并允许写回。

### 调光路径规划的整数模型

给定各路起始驱动级 `start_i ∈ [0, 255]`、终点线性 RGB `target`、等时步骤数
`K ∈ [2, 5]`、每步每路驱动变化上限 `Δ ∈ [1, 255]` 与共用容差 `tol`。
决策变量为第 k 步（`k = 1..K`）各路驱动级 `d[k][i] ∈ [0, 255]` 整数。

- 起点实际色（未裁剪公式，不取整）与第 k 步参考色（线性插值，**不先取整**）：

  ```text
  A0_c    = (Σ_i reading[i][c] · start_i) / 255 = S0_c / 255
  ref_k_c = A0_c + (target_c − A0_c) · k / K
  ```

- 每步实际分量 `s_k_c / 255`（`s_k_c = Σ_i reading[i][c] · d[k][i]`，整数分子）
  须落在参考色 ± 容差且 `0～1000` 内。窗口约束两边同乘 `255·K` 后完全整数化：

  ```text
  |K·s_k_c − T_k_c| ≤ 255·K·tol,   T_k_c = (K−k)·S0_c + 255·k·target_c
  0 ≤ s_k_c ≤ 255·1000
  ```

- 爬坡约束（首步相对起点）：`|d[k][i] − d[k−1][i]| ≤ Δ`，`d[0][i] = start_i`。
- 目标：最小化各步功率之和的整数分子 `Σ_k Σ_i power_i · d[k][i]`
  （实际 mW = 该值 / 255）。

求解前先做 K 次**预求解**：第 k 步无视爬坡约束时的最小功率 `lb_k`
（规模与单步配方求解相同），作为主模型中该步功率变量的下界以加速最优性
证明；若某步窗口本身不可行，则整条路径必然不可行，可直接判定。
结论三态（见 `app/path_solver.py`）：`optimal` 返回已证明总功率最小的完整
路径；`infeasible` 无完整路径；`incomplete` 搜索未证明最优——后两者都
**不返回任何步骤**。

## API

`POST /api/solve`，请求体示例：

```json
{
  "channels": [
    {"id": "R", "r": 1000, "g": 120, "b": 40,  "power_mw": 3200},
    {"id": "G", "r": 160,  "g": 1000, "b": 90, "power_mw": 2800},
    {"id": "B", "r": 60,   "g": 80,  "b": 1000, "power_mw": 3400},
    {"id": "W", "r": 820,  "g": 800, "b": 760, "power_mw": 6500}
  ],
  "target_r": 600,
  "target_g": 420,
  "target_b": 180,
  "tolerance": 12
}
```

响应主要字段：`feasible`、`channels[].drive`（驱动级，与输入同序）、
`sorted_ids`（字典序 tie-break 实际使用的 ID 顺序）、`actual_rgb`、`errors`、
`in_range`、`total_power_mw`、`power_num`（总功率的整数分子，实际功率
`power_num / 255`）。录入不合法返回 HTTP 422 并附字段级错误信息。

### `POST /api/robust/solve`

规划可承受**任意单路 LED 熄灭**的配方：一次联合求解正常方案与逐路熄灭
后的备用方案。请求体在 `/api/solve` 基础上增加 `max_adjust`
（故障后每路允许调整的最大驱动级差，`1～255`）：

```bash
curl -s http://localhost:8000/api/robust/solve \
  -H 'Content-Type: application/json' -d '{
  "channels": [
    {"id": "R", "r": 1000, "g": 120, "b": 40,  "power_mw": 3200},
    {"id": "G", "r": 160,  "g": 1000, "b": 90, "power_mw": 2800},
    {"id": "B", "r": 60,   "g": 80,  "b": 1000, "power_mw": 3400},
    {"id": "W", "r": 820,  "g": 800, "b": 760, "power_mw": 6500}
  ],
  "target_r": 450, "target_g": 450, "target_b": 450,
  "tolerance": 20,
  "max_adjust": 80
}'
```

`status` 三态：

| status       | 含义                                           | `normal`/`backups` |
| ------------ | ---------------------------------------------- | ------------------ |
| `optimal`    | 已证明正常总功率最小且逐路备用齐全的完整方案   | 均有值             |
| `infeasible` | 无完整容错方案（某路熄灭后无法配色或调整上限不足） | 均为空             |
| `incomplete` | 搜索未证明最优，**不返回任何正常/备用驱动级**  | 均为空             |

`optimal` 时响应主要字段：`channel_ids`（与输入同序，各驱动数组均按此序）、
`sorted_ids`、`normal`（正常场景，`failed_id` 为 `null`，含 `drives`、
`actual_rgb`、`errors`、`in_range`、`power_mw`/`power_num`、全 0 的
`deltas`）与 `backups[]`（与 `channel_ids` 一一对应，每个的
`failed_id` 为被熄灭的通道 ID、该路 `drives` 中对应项为 0，`deltas`
为相对正常驱动的各路差值，且 `|deltas[i]| ≤ max_adjust`）。
`max_adjust` 非 `1～255` 整数、通道数非 3～6、目标/容差越界等一律 HTTP 422。

### `POST /api/calibrate`

请求体只需通道 ID（满档 RGB 是被反求的对象）与 3～12 组样本；
`drives` 顺序与 `channels` 一致，`measured` 为四舍五入后的整数实测：

```bash
curl -s http://localhost:8000/api/calibrate -H 'Content-Type: application/json' -d '{
  "channels": [{"id": "R"}, {"id": "G"}, {"id": "B"}],
  "samples": [
    {"drives": [255,   0,   0], "measured": [1000, 120,  40]},
    {"drives": [  0, 255,   0], "measured": [ 160, 1000,  90]},
    {"drives": [  0,   0, 255], "measured": [  60,  80, 1000]},
    {"drives": [128, 200,  64], "measured": [ 643, 865, 342]}
  ]
}'
```

唯一时响应（`channels` 与输入同序，可直接写回通道表并保留原功率）：

```json
{
  "status": "unique",
  "channels": [
    {"id": "R", "r": 1000, "g": 120, "b": 40},
    {"id": "G", "r": 160,  "g": 1000, "b": 90},
    {"id": "B", "r": 60,   "g": 80,   "b": 1000}
  ],
  "message": "标定唯一：……可一键写回当前通道表（保留原功率）。"
}
```

`status` 四态：

| status          | 含义                                   | `channels` |
| --------------- | -------------------------------------- | ---------- |
| `unique`        | 已证明唯一，结果可用                   | 有值       |
| `contradictory` | 样本矛盾，不存在任何合法参数           | 空         |
| `non_unique`    | 存在多组合法参数，标定不唯一           | 空         |
| `unknown`       | 搜索未完成，**不得**据此判定矛盾或唯一 | 空         |

通道数非 3～6、ID 为空/重复、样本数非 3～12、驱动级非 `0～255` 整数、
实测非 3 个 `0～6000` 整数、驱动级数量与通道数不符等，一律 HTTP 422。

### `POST /api/path/solve`

联合求解从起始驱动级到终点色的等时调光路径（各步功率之和最小）。
`start_drives` 按通道 ID 给出，须与 `channels` 一一对应：

```bash
curl -s http://localhost:8000/api/path/solve -H 'Content-Type: application/json' -d '{
  "channels": [
    {"id": "R", "r": 1000, "g": 120, "b": 40,  "power_mw": 3200},
    {"id": "G", "r": 160,  "g": 1000, "b": 90, "power_mw": 2800},
    {"id": "B", "r": 60,   "g": 80,  "b": 1000, "power_mw": 3400},
    {"id": "W", "r": 820,  "g": 800, "b": 760, "power_mw": 6500}
  ],
  "start_drives": {"R": 0, "G": 0, "B": 0, "W": 0},
  "target_r": 600, "target_g": 420, "target_b": 180,
  "steps": 3,
  "max_step_delta": 40,
  "tolerance": 12
}'
```

`status` 三态：

| status       | 含义                                       | `steps` |
| ------------ | ------------------------------------------ | ------- |
| `optimal`    | 已证明各步功率之和最小的完整路径           | 有值    |
| `infeasible` | 不存在满足全部约束的完整路径               | 空      |
| `incomplete` | 搜索未证明最优，**不返回任何路径**         | 空      |

`optimal` 时响应主要字段：`channel_ids` 与 `start_drives`、
`start_actual_rgb`（起点实际色，未裁剪公式）、`steps[]`（按时间顺序，
含 `drives`（与 `channel_ids` 同序）、`actual_rgb`、`ref_rgb`（未取整的
插值参考色）、`errors`（实际 − 参考）、`in_range`、`power_mw`/`power_num`）、
`total_power_mw`/`total_power_num`（各步功率之和，实际功率 =
`total_power_num / 255`）。起始驱动级越界/缺漏/多余、步骤数非 2～5、
变化上限非 1～255、终点非 `0～1000`、容差非 `0～20` 等一律 HTTP 422。

## 显示说明

色块按**标准 sRGB 传递函数**显示：线性分量先除以 1000 归一化，再按
`c ≤ 0.0031308 ? 12.92c : 1.055c^(1/2.4) − 0.055` 编码为 8 位 sRGB。
若某个实际分量超出 0～1000（模型不裁剪），色块仅在显示时钳制到 0/255
并在悬停提示中说明；表格中的实际值与误差仍为未裁剪的精确值。

## 目录结构

```text
app/
  main.py        # FastAPI 应用与 /api/solve、/api/robust/solve、/api/calibrate、/api/path/solve、静态页面挂载
  solver.py      # CP-SAT 两阶段精确求解（配方）
  robust_solver.py # CP-SAT 单路熄灭容错联合求解（正常+逐路备用，最优/无完整方案/搜索未完成 三态）
  calibration.py # CP-SAT 满档读数反求（唯一/矛盾/不唯一/搜索未完成 四态）
  path_solver.py # CP-SAT 调光路径联合求解（最优/无完整路径/搜索未完成 三态）

static/
  index.html   # 页面结构
  style.css    # 样式
  app.js       # 通道编辑、容错/标定/路径规划调用、色块/误差/功率计算与手动预览
Dockerfile
docker-compose.yml
requirements.txt
test_solver.py       # 求解器冒烟测试（含 3 路穷举对照，可直接 python3 运行）
```
